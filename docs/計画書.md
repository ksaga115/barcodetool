## P1. iPhone ですぐ使える（PWA 化）

### 目的
アプリ化せず、Safari で開くだけ / ホーム画面に追加でネイティブ同然に使える状態。特に **カメラ読み取りを動かす**。

### 前提・制約（iOS Safari）
- `getUserMedia`（カメラ）は **HTTPS もしくは localhost 必須**。AirDrop で配った `.html` を Files から開く（`file://`）と **カメラは動かない**（生成とゲームは動く）。→ **HTTPS ホスティングが必須要件**。
- ホーム画面 PWA（standalone）でのカメラは **iOS 16.4 以降** で安定。16.3 以前は standalone だと失敗することがある（Safari で直接開けば旧版でも可）。
- iOS の ITP により、**約7日間アクセスがないと `localStorage` が消える**可能性。→ ゲームのコレクション保全のため **セーブの書き出し / 読み込み（JSONファイル）** を P3 で用意する。
- `100vh` + ノッチ: `viewport-fit=cover` と `env(safe-area-inset-*)` が必要（P5 の `native/z-native.css` と同じ考え方）。

### 方針
`BarcodeTool.html`（ネットワーク共有用の原本）は**改変しない**。P5 と同じく **ビルドで `web/` を生成** する。

- `scripts/build-web.mjs` を追加（`build-www.mjs` と同型）:
  - `<head>` に PWA メタと `manifest` リンク、`apple-touch-icon`、`apple-mobile-web-app-*` を注入。
  - `viewport` に `viewport-fit=cover` を付与。
  - `</body>` 直前に Service Worker 登録スニペットを注入。
  - `web/manifest.webmanifest` と `web/sw.js`、アイコン各サイズ（`assets/icon.svg` から生成）を出力。
- `web/manifest.webmanifest`:
  - `name` / `short_name` / `start_url: "./"` / `scope: "./"` / `display: "standalone"` /
    `orientation: "portrait"` / `theme_color: "#1e1e2e"` / `background_color: "#1e1e2e"` / `icons`（192, 512, maskable 512）。
- `web/sw.js`: **キャッシュ優先（cache-first）**、プリキャッシュは `index.html` + アイコン + manifest のみ。
  `CACHE_VERSION` を埋め込み、更新時は全入れ替え。オフライン完全動作（＝「外部通信なし」を維持）。
- 追加メタ（`<head>`）:
  ```html
  <link rel="manifest" href="manifest.webmanifest">
  <meta name="theme-color" content="#1e1e2e">
  <meta name="apple-mobile-web-app-capable" content="yes">
  <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">
  <meta name="apple-mobile-web-app-title" content="バーコードツール">
  <link rel="apple-touch-icon" href="icon-180.png">
  ```

### ホスティング（無料・独自サーバ不要）
- 第一候補: **GitHub Pages**（このリポジトリの `web/` を publish）。`https://<user>.github.io/BarcodeTool/` で公開、Add to Home Screen 可。
- 代替: Cloudflare Pages / Netlify（どれも静的・無料枠で十分）。
- 公開後、`start_url` とアイコンの相対パスが `/BarcodeTool/` サブパスで解決することを実機確認。

## P2. コードバトル刷新 v1.1（同一性を壊さない範囲）

### 最重要の制約
**`CB.build()` に手を入れると、既存の全個体（名前・属性・ステータス）が変わる。**
「同じコードは、いつでも同じ個体」が看板なので、生成ロジックの変更は P4 の「図鑑リフレッシュ」まで**やらない**。
v1.1 は **対戦の数式・UI・変動性・コレクション運用** だけを変える（＝個体IDは不変、無風で移行できる）。

### 現状の課題（分析）
1. **プレイヤーの関与がない**: 読み取る→完成体が出る→自動対戦→勝敗記録、の一本道。積み上げ・選択・育成がない。
2. **試合が完全固定**: 同じ2体は毎回まったく同じ結果。1回見たら再戦の意味がない（個体の決定論は良いが、**試合単位の決定論は再戦性を殺す**）。
3. **TOTAL 一元化が設計思想と矛盾**: 「見た目で強さは分からない」と言いつつ、並び替え・「最強」表示・「上位2体で対戦」が TOTAL 依存。
4. **ステータスの意味が濁っている**: TEC は攻撃・命中・回避耐性・特性2種に、LUK はクリティカル・行動順・同値判定・回避に絡む。プレイヤーが狙いを持てない。
5. **属性が学習しづらい**: 6すくみで「真裏（+3）が無効果」は直感に反する。倍率（1.26/1.10/0.90/0.80）も1v1では見えない。
6. **コード内容と個体が結びつかない**: 風味は全部ハッシュ由来で不透明。「4901…」を見て何も予想できない → スキャンに意図が乗らない。
7. **対戦演出が地味**: 2.6秒のテキストログのみ。見せ場なのに平坦。
8. **`count`（再スキャン回数）が無機能**: 同じ商品を何度も読む行為に報酬がない。
9. **800体で record なし個体を無言削除**: コレクターに不安。フラット一覧で 800 は多すぎて回遊しづらい。
10. **戻ってくる理由がない**: デイリー、目標、ラダー、縄張りなどのループがゼロ。

### v1.1 でやること（すべて対戦数式・UI 側 = 個体不変）

**A. 試合に変動性を入れる（再戦性の回復）**
- 試合シードを `hash(A) ^ hash(B) ^ matchSalt` にする。`matchSalt` は「その日付インデックス」＋「この組の対戦回数」。
  → 同じ組でも日替わり・再戦ごとに展開が変わる。A/B対称性は維持（`min/max(hash)` の作法は継続）。
- **3本勝負**（Best of 3）: 1試合＝3サブシード。番狂わせと締まりが出る。
- 決着理由（`reason`）の生成はそのまま活かす。

**B. ステータスの役割を1つずつに整理（表示と数式のみ）**
- ATK = 与ダメージ。DEF = 被ダメージ軽減 + 最大HP。SPD = 行動順 + 回避。
  TEC = 命中 + 防御貫通（`calc` 相当を一般化）+ ダメージ分散を狭める（安定）。
  LUK → **FOC（集中力）に改称**: クリティカル率・倍率と“振れ幅”だけを担当。
- 各ステータスに1行の説明を UI に出す（「SPD: 先手と回避」等）。
- **注意**: 改称は表示だけ。`STAT_KEYS` の内部キー順を変えると `permutation()` 経由で既存個体の数値が変わるため、内部キーは維持し表示ラベルだけ差し替える。

**C. 属性を学習可能に（倍率だけ変更、割り当ては不変）**
- 6すくみは維持しつつ「真裏（+3）＝相互に弱め合う拮抗（×0.90 / ×0.90、長期戦）」に意味づけ。
  次（+1）＝×1.20、+2＝×1.00、−1（+5）＝×0.80、−2（+4）＝×0.95。
- 対戦画面に属性関係を明示（「烈火 → 機甲 有利 ×1.20」）。ダメージ数値と有利表示は既に一部あるので拡張。

**D. 見せ場を少しだけ盛る（アプリの静かな世界観は保つ）**
- HPバーのドレイン、会心のフラッシュ、決着の1カット。CSSアニメ中心、重い演出はしない。
- ログは「T3  烈火 → 機甲 有利  ガル…の一撃 42（会心）」のように属性・会心・連撃を色/記号で区別（既存構造を流用）。
- 「スキップ」は継続。全体2.5〜3秒のテンポ維持。

**E. コレクション運用の改善**
- 上限を 800 → 2000 に引き上げ、超過時は**無言削除をやめて「アーカイブ」**（別リストに退避、復元可）。
- 一覧に**フィルタ**（属性 / 特性 / ランク / コード種別 / 未対戦）。
- 発見時トーストに**レア度の理由**を1行（例: 「チェックディジット一致 / 回文 / 長文」など、コード内容から今すぐ言える事実）。
- `count`（再スキャン）に軽い意味: 同一個体を N 回読むと「熟練度」が上がり、**対戦の“振れ幅”がわずかに縮む**（強くはならない＝pay-to-win 回避、通い箱スキャンに小さな報酬）。

## P3. モバイル品質パス

### 検出済みの具体的な弱点
- **文字が小さい**（body 13px）。タップ標的が小さい。ヘッダーにボタン6〜7個が横並び → narrow で破綻。
- `user-select: none` が全体に効いて、**読み取ったテキストを選択コピーできない**（結果欄は選択可にする）。
- `title` ツールチップ依存 → タッチでは出ない。重要情報は可視ラベル/サブテキストへ。
- レイアウトがデスクトップ前提: `#dec-left`/`#dec-right`、`#game-left`/`#game-right` の横並び → 縦積みのブレークポイントが要る。
- モバイルでの主用途は**カメラ読み取り**なのに2番目のタブ。狭い画面では読み取りを初期表示にする / 大きな「スキャン」導線を出す。
- **セーブの書き出し / 読み込み**が無い（PWA の ITP 退避対策として必須。生成プリセットとゲーム両方）。
- アクセシビリティ: コントラスト、`aria-label`、フォーカス可視、色だけに依存しない状態表示。
- iOS では「写真ライブラリから画像を選んで読み取る」導線があると便利（`<input type="file" accept="image/*">` は既存、`capture` 無しで選べることを確認）。

## P4. コードバトル v2 — 方向決定: **方向2（スカッド + デイリー・ガントレット）**

2026-09-04 決定。v1.1（P2）は共通で進め、v2 でこの軸に乗せる。

v2 は **生成ロジックにも手を入れる**ため、「図鑑リフレッシュ」（既存個体の一度きりの作り直し）を伴う。
**インストールベースが小さいうちに、P1 公開と同じタイミングでやるのが傷が浅い。**
生成に入れたい legibility（下記）:
- 属性を **コード種別 + 先頭情報から読める**表に一部依存させる（例: JAN の国コード帯、`http(s)://`、ISBN、純数字、テキスト → 系統がなんとなく予想できる）。ステータス・特性はハッシュ由来のまま。
- レア度ルールを明文化（有効チェックディジット / 回文 / 特定コード種 / 長文 など）→ 狙って集められる。

### 採用: 方向2 — スカッド戦術 + デイリー・ガントレット
- 対戦を **3体編成**に。前衛が受け、後衛が特性で支援（`呪詛`+`蝕毒` の重ね、`城壁`前衛+`猛牙`後衛 など）。
- **共鳴**: 同じスキャンセッション / 同じ商品カテゴリ帯の個体を一緒に編成すると小ボーナス → 棚ごとスキャンに意味。
- **デイリー・ガントレット**: 日付シードで生成される“野良スカッド”に挑戦。自分の編成は自動防衛。毎日リセット＝戻る理由。
- 個体の決定論は維持、試合変動は日付シード。
- 採用理由: 「世界のバーコードをスキャンする」行為が「毎日開く理由」に変換される／決定論資産を再利用できる／共鳴が実利用（棚ごとスキャン）に接続する。

### 検討したが不採用
- **方向1（1v1 のまま締める）**: P2 で概ね達成できるため v2 としては不足。
- **方向3（図鑑コンプ / アイドル寄り）**: 静かなトーンには最適だが継続の引きが弱い。※図鑑・レア度・週目標のアイデアは方向2に部分的に取り込む。
- **方向4（ローグライト・ラン）**: 単体ゲームとしての引きは最強だがトーンの変化が大きく、実利用（スキャン）との接続が薄い。

### v2.5 — 進化・強化（育成レイヤー / v2 の後）
ユーザー要望。**素体（コード由来）は不変**のまま、進化・強化は**セーブ側の別レイヤー**（いつでも素体に戻せる・課金なし）。
- 系統ゲージ: `family`＋属性ごとの所持コード数がしきい値（3/8/20種）で進化段階を解放。
- 進化 `evo:0..3`: 称号（既存 `TITLES` 流用）＋上限つきステボーナス＋進化3で第2特性。
- 欠片: 余剰個体をアーカイブ解放して入手 → 進化コスト / 微強化（+1ステ、ハードキャップ）/ 研磨（振れ縮小）。
