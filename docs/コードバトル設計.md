# コードバトル 詳細設計

最終更新: 2026-09-04 ／ 上位計画: `docs/計画書.md` P2・P4

このドキュメントは実装前の設計仕様。数値は初期値で、シム（V6）で調整する。

---

## 0. 貫く柱（変えない）

1. **個体の決定論**: 同じコード内容 → 同じ個体（名前・属性・ステータス・特性）。いつでも・どの端末でも。
2. **強さは一目では分からない。ただし“学べば読める”**（不透明ではなく、努力で予測可能）。
3. **Pay-to-win なし / 個体ガチャなし**。手に入るのはスキャンしたぶんだけ。
4. **オフライン・通信ゼロ**。すべてローカルで決定論的に計算。
5. **静かな見た目を壊さない**。演出は最小限。

## 0.1 実装上の絶対制約

`CB.build()`（生成関数）に触ると**既存の全個体が変わる**。以下を厳密に分ける:

| 変更対象 | 個体への影響 | 移行 |
|---|---|---|
| `battle()` の数式、`mkFighter` の HP 式、`affinity()` の倍率、表示ラベル、`store` への**追加**フィールド | なし | 不要（`barcode_codebeast_v1` のまま） |
| `build()` 内の `elemIdx` / `permutation` / `raw[]` / 名前生成 / `STAT_KEYS` 配列 | **全個体が生まれ直す** | **図鑑リフレッシュ**（`_v2` へ key 昇格、一度きり、アプリ内告知） |

→ **v1.1 は上段のみ**。**v2 で下段に踏み込む**（属性のコード種別依存のため不可避）。

# v1.1 — 対戦の数式・UI・変動性（個体不変・移行なし）

## V1. 試合の変動性 ＋ Best of 3

**問題**: `battle(A,B)` は (A.hash, B.hash) だけの純関数。毎回まったく同じ。再戦の意味がない。

**設計**:
- 1 **マッチ** = 3 ゲームの2本先取。各ゲームに独立シード。
- ゲームシード:
  ```
  pairKey  = mix(min(A.hash,B.hash), max(A.hash,B.hash))   // A/B 対称は維持
  dayIndex = floor(localMidnightEpoch / 86400000)
  rematchN = store.rematch[pairKey]  (BATTLE 押下ごとに +1、LRU 500 件で剪定)
  gameSeed[k] = mix(pairKey, dayIndex, rematchN, k)          // k = 0,1,2
  ```
  → 同じ2体でも「翌日」「再戦」で展開が変わる。同日・同 rematchN なら再現可能（デバッグ・共有用）。
- **決着**: 先に2ゲーム取ったほうがマッチ勝ち。1-1 なら第3ゲーム。マッチ結果＋各ゲーム結果を表示。
- 既存 `battle()` コアはそのまま使い、`sm32(...)` の種を `gameSeed[k]` に差し替えるだけ。
- 新ランダム要素は足さない（回避・ダメージ振れ・会心・連撃・行動順同値、が種替えで自然に分岐）。
- `store.rematch` は `barcode_codebeast_v1` への**追加**フィールド（後方互換）。

**狙い**: TOTAL 差 ~10 で「格下が3ゲーム中1つは取れる」程度の変動。振れ幅は下の技/運で制御。

## V2. ステータスの役割を1つずつに（表示ラベル＋数式のみ）

**内部キー `["ATK","DEF","SPD","TEC","LUK"]` は順序・数とも不変**（`permutation()` 経由で既存個体が変わるため）。**表示ラベルと `battle()` 内の意味だけ**変える。

| key | 表示 | 一言 | 対戦での効果 |
|---|---|---|---|
| ATK | 攻 | 与ダメージ | ダメージ基礎（線形） |
| DEF | 守 | 被弾軽減・体力 | 軽減カーブ ＋ 最大HP |
| SPD | 速 | 先手・回避 | 行動順（＋`韋駄天`）／回避率 |
| TEC | 技 | 命中・貫通・**安定** | 命中（回避を相殺）／守を最大35%貫通／**自分のダメージ振れを狭める** |
| LUK | 運 | 会心・**振れ幅** | 会心率・倍率／**自分のダメージ振れを広げる**／同値タイブレーク |

- **技 ⇄ 運 を“安定 vs 一発”の対立軸に**。「攻＋運・技低 ＝ 振れる紙装甲」のように狙いが持てる。
- 行動順から運を除去（現 `spd + luk*0.06` → `spd` のみ ＋ `韋駄天`）。
- ダメージ基礎から技を除去（現 `atk*0.92 + tec*0.44` → `atk * c`）。

**数式（初期値・要シム調整）**:
```
spread    = 0.16 * (1 + LUK/100*0.9 - TEC/100*0.7)      // ≒ 0.05 .. 0.28
dmgRoll   = 1 - spread + rnd()*2*spread
hitChance = clamp(0.88 + TEC*0.0010 - df.SPD*0.0016, 0.60, 0.99)   // 外れ = df.dodges++
pierce    = TEC/100 * 0.35
defEff    = df.DEF * (1 - df.defDrop) * (1 - pierce)
mitig     = 150 / (150 + defEff * 1.35)
crit      = clamp(0.03 + LUK*0.0030, 0, 0.30)
critMult  = 1.5 + LUK/100 * 0.5                          // 1.5 .. 2.0
```
既存 trait 補正（`fang` ×1.12 等）はこの上に乗せる。最終調整は V6。

## V3. 属性 — 学べる6環（倍率と UI のみ、割り当ては不変）

`elemIdx` の割り当ては据え置き（`build()` 内）。`affinity()` の倍率と表示だけ変更。

環: 機甲(0)→烈火(1)→深水(2)→雷電(3)→深闇(4)→聖光(5)→機甲。`d = (b - a + 6) % 6`。

| d | 関係 | 倍率 | 意味 |
|---|---|---|---|
| 0 | 同系 | ×1.00 | — |
| 1 | 克（次） | ×1.25 | 一方的に有利 |
| 5 | 被克（前） | ×0.80 | 一方的に不利 |
| 2 | | ×1.05 | わずかに有利 |
| 4 | | ×0.95 | わずかに不利 |
| 3 | 対極 | ×0.90（両方向） | 相殺・長期戦 |

- 覚える規則は1文: **「自分の“次”に強い。“対極”（真裏）とは拮抗して長引く」**。
- UI: 対戦画面と個体カードに6環の小図（自分の位置＋克/被克の矢印）。攻撃ログで `|倍率-1|>0.05` の行に `烈火→機甲 克 ×1.25` タグ。

## V4. 対戦の“なぜ”を見せる

- 試合後パネル（コンパクト）: ゲームごとに 勝者/ターン数/決着種別（撃破/判定/相打ち）＋MVPステータス。
  合計: 与ダメージ・会心数・回避数・最大の一撃・適用された属性倍率。
- 既存の `reason` 文言は残す（数値の裏付け付きで）。
- 演出: HPドレイン（残像バー）、会心フラッシュ＋大きめ数字、属性有利は色、`連撃`=「連」、DoT はティック表示。全体 ~3秒維持、スキップ継続。

## V5. コレクション — 集める人を罰しない

- `MAX_ENTRIES` 800 → **2000**。
- 超過は `delete` をやめて `store.archive` へ退避（同形・別オブジェクト）。アーカイブは一覧非表示・防衛不参加・**復元可**。アーカイブ自体のハード上限 5000、超過時のみ「戦績なし・古い順」で削除。
- 一覧に**フィルタ**チップ: 属性 / 特性 / ランク帯 / コード種 / 未対戦 / アーカイブ。
- `count`（再スキャン）→ **熟練度**: `mastery = min(5, floor(log2(count+1)))`。効果は**その個体のダメージ振れを 2%/lv 縮める（最大 −10%）＋命中 +1%/lv 上限 +3%**。**素ステータスは絶対に上げない**（通い箱スキャンへの微報酬）。
- 発見トーストに**レア度の理由**（コード内容から今言える事実のみ、生成非依存）:
  「有効なチェックディジット」「回文」「全桁同一」「長文（N文字）」「コード種: DataMatrix」等。

# v2 — スカッド ＋ デイリー・ガントレット（図鑑リフレッシュ必須）

## S0. 図鑑リフレッシュ（一度きりの移行）

理由: v2 で**属性をコード内容から一部読めるようにする**（S3）→ `build()` の `elemIdx` 派生が変わる → 全個体が生まれ直す。

- 保存キー `barcode_codebeast_v1` → `barcode_codebeast_v2`。
- v1 データがある状態で初回 v2 起動 → 一度きりのモーダル:
  「図鑑を作り直します。集めたコード（N件）と戦績は引き継がれ、各個体の姿が新ルールで生まれ直します。」OK のみ。
- 引き継ぐ: `code / first / count / wins / losses / label / kind`。個体は `build_v2(code)` で遅延再生成（従来同様キャッシュ）。
- `barcode_codebeast_v1` はディスク上に**1バージョンだけ残す**（ロールバック用）。次版で削除。
- 勝敗は「同じコードの再顕現」として引き継ぐ。

## S1. スカッド = 3体・配置

- スロット: **前衛 / 中衛 / 後衛**。対戦は スカッド vs スカッド の自動解決。
- **前衛**が被弾。前衛撃破で中衛→前衛、後衛→中衛と繰り上げ。3体全滅で敗北。
- **中衛/後衛**は直接は殴られない（繰り上がるまで）。ただし**特性がベンチから弱めに発動**（S2）。
  → 脆いがオーラ特性が強い個体は後衛向き、という編成パズル。
- 各ターンの攻撃は**両陣営とも現・前衛1体のみ**（現行 `strike()` をほぼ流用）。行動順は前衛の 速。
- ラウンド上限 ~36。再生は 1ゲーム ~2秒目標（ステップ高速化）。

## S2. 配置による特性の効き方（シナジー）

16特性を「前衛（本発動）」と「ベンチ（オーラ、約40%）」に整理:

| 特性 | 前衛 | 中/後衛オーラ |
|---|---|---|
| 城壁 | 被ダメ −12% | 隊全体 被ダメ −5% |
| 猛牙 | 与ダメ +12% | 前衛 与ダメ +5% |
| 韋駄天 | 行動順↑・先制 | 隊 行動順 微↑ |
| 演算 | 敵 守 −25% | 前衛 敵守 −10% |
| 天佑 | 会心↑ | 隊 会心 微↑ |
| 逆鱗 | 低HPで威力ランプ | —（前衛限定） |
| 連撃 | 稀に2回攻撃 | — |
| 呪詛 | 敵守をターンで削る | **ベンチでも敵前衛の守を微削り**（蝕毒と累積） |
| 再生 | 自己回復/ターン | 現・前衛を微回復/ターン |
| 重撃 | 威力↑速↓ | 前衛 威力↑速↓（小） |
| 反射 | 被ダメの一部返し | 現・前衛が微反射 |
| 明鏡 | 敵会心↓・回避↑ | 隊 敵会心↓（小） |
| 不屈 | 一度だけHP1で耐える | —（前衛限定） |
| 蝕毒 | 敵最大HPを削る | **ベンチでも敵前衛の最大HPを微削り** |
| 集中 | 技→命中・威力 | 前衛 命中 微↑ |
| 疾撃 | 速→威力 | —（前衛限定） |

意図: **オーラ型**（呪詛/蝕毒/再生/明鏡/城壁/猛牙）は脆い担ぎ手でベンチに置くのが強い。**前衛限定型**（逆鱗/連撃/不屈/疾撃）は硬い担ぎ手が要る。

**明示シナジー（小・命名・編成 UI で表示）** ~6個に限定:
- 城壁(前) ＋ 任意オーラ(後) → 「要塞陣」: 隊 被ダメ 追加 −3%
- 呪詛 ＋ 蝕毒（どこでも） → 「崩壊」: 敵前衛の 守/HP 侵食 +50%
- 猛牙(前) ＋ 演算(ベンチ) → 「貫通陣」: 確定ダメージ +8%
- 韋駄天(前) ＋ 天佑(ベンチ) → 「先制必中会心」
- 再生(ベンチ) ＋ 明鏡(ベンチ) → 「静養」: 前衛 再生 +50%
- 疾撃(前) ＋ 韋駄天不在 → 「単騎疾駆」: 速→威力 変換率↑

## S3. 共鳴 — ゲームを“実際にスキャンすること”に結ぶ

発見時に各エントリへタグ2種を付与:
- `session`: スキャンセッションID。最後のスキャンから ~10分、またはタブ離脱で更新。→ 同じ買い物のコードは同一セッション。
- `family`: **コード内容から読める**分類:
  - EAN/JAN-13: GS1 先頭帯 → `JAN:45x`（日本 45/49）, `JAN:00x`（US/CA）…
  - ISBN(978/979) → `BOOK`
  - `http(s)://` → `URL:<TLD>`（例 `URL:jp`）
  - 非EANの全数字 → `NUM:<桁帯>`
  - Code128/93/39 の英数 → `TEXT`
  - 構造化QR（`WIFI:` `MECARD:` `geo:` `tel:`）→ `QR:<種別>`
  - その他 → `MISC`

**共鳴ボーナス**（対戦時のみ、小さめ）:
- 3体が同一 `family` → 「同族共鳴」: 実効全ステ +6%
- 3体が同一 `session` → 「同刻共鳴」: 先制 +1 ＋ 隊 与ダメ +4%
- 3体中2体一致 → 半分

→ 棚ごと一気にスキャンすると自然に共鳴隊ができる。**非共鳴でも普通に戦える**程度の差。

## S4. デイリー・ガントレット

- **ローカル日ごと**に敵スカッド5段を生成（`dayIndex` シード → 同じ日付なら同じ梯子。オフラインの緩い共通体験）。
- 敵は `dayIndex` 由来の疑似コード（例 `"GNT-<day>-<rung>-<slot>"`）を `build_v2` に通した**本物の個体**。段が上がるほどステ予算↑（段1 ≒ 自分の中央値、段5 ≒ 自分のコレクション上位四分位にスケール）。
- 自分のスカッドを選んで上から挑戦。負けたらその日はそこで終了。
- **報酬（Pay-to-win 回避、コスメ/メタのみ）**:
  - 段1–2: 「調査記録」ポイント → 図鑑ロア解放、カードの縁飾り
  - 段3: **改名トークン**（愛称。元のコード名はサブタイトルに残す）

# v2.5 — 進化・強化（育成レイヤー）

ユーザー要望: 「同系統が集まったら進化」「強化」。

## 柱1との整合（重要）

「同じコード＝同じ個体」は**素体（そたい）＝コードから決まる不変の真形**として維持する。
進化・強化は「その個体をどう育てたか」＝**セーブ側の別レイヤー**。常に素体を確認でき、いつでも素体に戻せる。

- `build_v2(code)` → 素体（決定論・不変）
- エントリの育成フィールド `evo: 0..3`, `boost: {ATK:+n,...}`, `polish: 0..5` を素体の上に重ねて実効値を出す
- セーブを失うと素体に戻る（P3 のバックアップ機能で担保）
- **課金は一切なし**。素材は自分のコレクションとプレイからのみ

## E1. 系統（lineage）と系統ゲージ

- 個体の**系統** = `family` タグ（S3: `JAN:45x` `BOOK` `URL:jp` `TEXT` `QR:wifi` …）＋ 属性。
- 系統ごとに「所持している**別コード**の数」をカウント → **系統ゲージ**。
- しきい値で、その系統の個体の**進化段階**を解放:
  - 3種 → 進化1 解放
  - 8種 → 進化2 解放
  - 20種 → 進化3 解放
- しきい値は「解放（できるようになる）」だけ。実際の進化には欠片を払う（E3）。
  → 幅広くスキャンするほど育成の選択肢が増える（1体グラインドより収集が効く）。

## E2. 進化（evolution）

- **個体ごとに任意**。`evo` を 0→1→2→3 に上げる。見た目と実効ステが変わる。
- 名前: 既存 `TITLES`（`・零式 / ・改 / ・II / ・双牙 / ・古体 / ・変異 / ・原種`）を段階の称号として流用。素体名は常に併記。
- ステ上限つきボーナス（その個体自身の偏りに沿って配分）:
  - 進化1: 実効 +6 / 進化2: 累計 +14 / 進化3: 累計 +24
- 進化3 で**第2特性スロット**: その系統に多い特性の弱い版を1つ得る（`TRAITS` から系統頻度で決定論的に選ぶ）。
- コスト: **系統の欠片**（E3）。しきい値解放済みが前提。

## E3. 強化（strengthening）と欠片（shards）

- **欠片の入手**:
  - 余剰個体を**アーカイブ→解放**すると、その系統の欠片に変わる（枠整理が資源になる）
  - ガントレットの段報酬（S4）
  - ※再スキャン＝熟練度（V5）とは別系統。混ぜない。
- **使い道**:
  - 進化のコスト（E2）
  - **微強化**: 1ステータス +1（現在値が高いほど高コスト）。**素体+15 / 個体合計 +X のハードキャップ**。
  - **研磨（polish）**: ダメージ振れを購入で縮める（熟練度と同枠・合算上限あり）
- **ハードキャップ厳守**: 強化しきったコモンでも、無強化の SS を超えない。目的は「お気に入りとの差を詰める」であって青天井の成長ではない。

## E4. アンチ崩壊 / 数値方針

- 実効ステ = clamp(素体 + evoボーナス + boost, 1, 素体+一定, かつ全体上限)。
- スカッド実効合計のソフトキャップ（S6）は育成後の値で判定 → 育成済み3強を並べても頭打ち。
- V6 シムは「フル育成コモン vs 無育成レア」を必ず検証項目に入れる。

# v3 — 技（攻撃手段）・相性の深掘り・一発逆転（2026-09-04）

ユーザー要望:「もっと相性という要素や一発逆転という要素を追加したい。攻撃手段を増やすことで対応したい、ポケモンみたいに」。

## 設計方針
- **全自動対戦のまま**にする（「対戦は自動」という柱は崩さない）。プレイヤーが技を選ぶのではなく、**エンジンが状況に応じて自動選択**する——見ている側には「考えて技を選んでいる」ように映る。
- **`build()` は変更しない層に追加する**（＝図鑑リフレッシュ不要）。`moves` は既存の計算がすべて終わったあとに、既存のハッシュ材料（`S[]` / `hAll` / `f`）から**追加で**導出するだけで、名前・ステータス・属性・特性・hash など既存のどのフィールドにも影響しない。実際にシムで TOTAL 分布・ランク分布・属性分布・系統の legibility が導入前後で統計的に同一であることを確認済み（`v2test.mjs`）。

## 技（moves）の仕様
- 1個体につき **3つの技**。1本目は必ず自分の属性（十八番／STAB相当）、2・3本目は別のハッシュ材料から独立に決まる属性（＝本来の属性と異なる「カバー技」になり得る）。
- 技の種類（kind）は5つ、個体ごとに3つ（重複なし、確率は均等ではない）:

  | kind | 名前接尾 | 効果 |
  |---|---|---|
  | strike | 打撃 | 素直な一撃（基準） |
  | crit | 会心撃 | 会心率 +9pt |
  | pierce | 貫通撃 | 守備をさらに14%多く無視 |
  | drain | 吸収撃 | 与ダメの35%を自分が回復 |
  | finisher | 渾身の一撃 | 威力 ×1.75。**自分のHPが18%以下（背水の陣中は28%以下）のときしか選ばれない** |

  種類選択は重み付きプール（`MOVE_KIND_POOL`）で、finisher は他の4種より出現率を落としてある（狙い: 個体の 25〜35% 程度が渾身の一撃を持つ）。

## 相性（技ベースの自動選択＝カバー技）
- ダメージの属性相性は、**その個体固有の属性ではなく「使った技の属性」**で決まる。毎回の攻撃で、瀕死でなければ `chooseMove` が**相手の属性に対して最も有利な技（威力係数込み）を自動選択**する。
  → 同じ個体でも、相手が変われば繰り出す技（＝有効な属性）が変わる。これが「ポケモンの技構成でカバーする」体験の自動対戦版。
- 効果は数値でも確認済み: カバー技導入前は「属性有利時の勝率 − 不利時の勝率」が **約45pt**（同TOTAL帯）あったが、導入後は **約15pt** に自動的に縮小した（不利な相手には別の技に切り替えるため）。これは意図した副作用で、前回のバランス調整で下げきれなかった属性依存の強さを technique 面から解決した形。

## 一発逆転（渾身の一撃・背水の陣）
- **渾身の一撃**: 上記の通り、瀕死のときだけ自動選択される大技。ログには「！！」付きで表示され、専用の色（赤・太字）でハイライトされる。
- **背水の陣**（Best of 3 の跨ぎ）: `match()` / `squadMatch()` が**直前のゲームで負けている側**を判定し、そのゲームだけ `desperate` フラグを立てる。効果:
  - ダメージ +5%、会心率 +3pt
  - 渾身の一撃の発動しきい値が 18%→28%（1v1）に緩和（早めに大技へ踏み切れる）
  - スカッドでは隊全員に効く
  - 判定は「A/Bどちらが負けているか」という**相対状態**から決まるため、A/B を入れ替えても対称性は保たれる（シムで確認）。
- 決着理由（`reason`）に新しい文言を追加: 「背水の陣からの大逆転」「渾身の一撃が決め手になった一発逆転」。`favHits`（有利技を当てた回数）・`finisherHits` を個体に記録し、これらを reason 判定に使う（旧来の battle 全体に対する固定属性値 `affA`/`affB` は廃止）。

## UI

- 個体の詳細カードに**技一覧パネル**を追加（`movesPanelHtml`）。属性マーク・技名・効果の短文。渾身の一撃は赤枠で強調。TOTAL 数値を出さない方針（前節参照）と両立する、非数値の「読みもの」情報として機能する。

# v4 — ランク別育成コスト・融合（2026-09-05）

ユーザー要望:「らんくによって育成難易度が違うのがわからないのあれだな」「融合機能とかもほしい」「進化とか融合ツリーとか見れたら楽しそう」。

## ランク別育成コスト
それまで進化・強化・研磨のコストはランクを一切見ていなかった（進化は段階のみ、強化は実効ステ値のみ、研磨は定額）。**素体のランク**（育成前の固定値。育成しても変わらない）に応じてコストが上がるようにした。
- `RANK_VALUE`：E=0, D=1, C=2, B=3, A=4, S=5, SS=6
- `evoCost(code, stage) = EVO_COST[stage] + rankValue*stage`（段階が上がるほどランクの影響も拡大。例: D進化3=13 / S進化3=25）
- `boostCost` に `+floor(rankValue/2)`、`polishCost` に `+floor(rankValue/3)` を加算
- 詳細カードの育成パネルに「この個体は◯ランク。ランクが高いほど…コストは上がります」という説明文を追加（数字だけでなく理由も見えるように）
- 判定は常に**素体のランク**。育成して総合力が上がってもコストが雪だるま式に増えていく、という嫌な連鎖にはしていない

## 融合
2体を1体にする新機能。既存の「同じコード＝同じ個体」の柱を壊さないよう、**融合結果も決定論的に導出される仮想コード**として実装した。

- `fusionCodeOf(codeA, codeB)`：2つのコードを辞書順に並べ替えてから `"FUSION:" + 長さ + ":" + 短い方 + ":" + もう一方` の形に結合し、`CB.normalize` にかける。**順不同**（A融合B＝B融合A）かつ**決定論**（同じ2体は何度融合しても必ず同じ結果）。長さプレフィックスで文字列境界の偶然の衝突を回避。
- 融合結果は普通のコードとして `CB.beastOf()` にそのまま通る＝ステータス・属性・特性・技はすべて既存の生成ロジックがそのまま生む。新しい生成規則は書いていない。
- 融合結果の `family` は一律 `"FUSION"`。系統ゲージ（進化解放）が融合専用に積み上がっていく。
- **コスト**：`fusionCost = 5 + rankValue(親A) + rankValue(親B)`。欠片は親Aの系統から優先して引き落とし、不足分を親Bの系統から。
- **親の扱い**：消滅ではなく**アーカイブへ退避**（`store.beasts`から削除して`store.archive`へ）。同じコードを再スキャンすれば単体としてそのまま復活する。コレクションの実数は「親2抜け子1増」で -1 になる。
- 同じ組み合わせを二度融合することはできない（`store.beasts`/`store.archive`のどちらかに既にあれば拒否）。

## UI
- ⚔タブに4つ目のモード「融合」を追加（1体対戦／スカッド／今日の挑戦／融合）。
- 2スロット（親A・親B）にコレクションから選択→タップで配置。コスト・不足時の理由をリアルタイム表示。
- **系譜**：`allFusionEdges()` がコレクション＋アーカイブ全体から `fusedFrom` を持つ個体を走査し、「親＋親→子」の行を一覧表示。子ノードをタップするとその個体を選択して1体対戦モードへ移動。深い多世代ツリー（親のそのまた親…）までは描画せず、直近1代のみを一覧表示するミニマムな実装（安全に検証できる範囲に抑えた。将来的に世代を遡る表示に拡張余地あり）。
- 個体の詳細カードに「融合由来 — 親A ＋ 親B」の表示を追加。

## 実装中に見つけた実バグ（シムで発見・修正）
- **`discover()` が新規個体のオブジェクトに `evo`/`boost`/`polish` を含めていなかった**：`seedSamples()` や `parseEntry()`（保存→読込後）は正しく含んでいたが、実際にコードを読み取って**新規発見した直後**（保存/再読込前）の個体だけがこれを欠いていた。育成パネルを開く・育成ボタンを押すと `undefined` プロパティアクセスで例外。domcheck で融合テスト用に新規発見したコードを使った瞬間に発覚。→ `discover()` の新規エントリ生成に3フィールドを追加して解消。他の生成箇所（`doFuse`・`seedSamples`）は元々正しかった。

## 仕組み
- 自分の「スカッド」（3体編成）を、決定論的な**挑戦状**という文字列（`CBX1:` + JSON）に書き出せる。中身は3体ぶんの `{code, evo, boost, polish}`（＝育成状況込みのスナップショット）だけで、新しい生成ロジックは一切持たない。

勝利時、編成3体の系統に欠片を付与。同じ相手からは1日1回まで（詳細は同節参照）。

## 名前 — 形容詞＋日常のありふれた名詞
最初は「実在する単語2つを直接くっつける」案（例：灼熱＋鏡→「灼熱鏡」）で作ったが、ユーザーから**「聞き慣れない組み合わせになる」「漢字だけだと距離感がある」「広辞苑である意味がない」「似たようなものができちゃう」「形容詞＋名詞で、かわいい宮城県・おざなりなフランスパンみたいな適当さがいい」**とフィードバックがあり、以下の形に着地した。

- **`名前 = 形容詞 + 名詞`**（例：かわいい＋宮城県→「かわいい宮城県」、おざなりな＋フランスパン→「おざなりなフランスパン」）。壮大なファンタジー風にはせず、あえて気の抜けた・ちぐはぐな面白さを狙っている。
- `NAME_PREFIX`＝よくあるい形容詞・な形容動詞（そのまま名詞の前に直接付けられる形＝「な」まで含めて保持）。`NAME_SUFFIX`＝日常のありふれた名詞（都道府県・食べ物・動物・植物・身の回りの物・体の部位・衣服・乗り物・職業・スポーツ・地形など、系統立てたカテゴリで網羅）。
- **広辞苑そのもの（著作権のある市販の辞書）のデータは存在せず、埋め込めない**——これはユーザーへの説明が必要な事実。無料で使える辞書データ（JMdict等）はあるが、数万〜十万語規模でサイズが大きく、この単一HTMLファイルに埋め込むのは現実的ではない。代わりに「広辞苑に載っていそうな一般的な単語」を手作業で選ぶ方式を採用。

# v8 — TOTAL差ごとの勝率をなだらかに（2026-09-05）

ユーザー要望:「TOTAL差ごとの強いほうの勝率をもっと低くしてほしい。0-3くらいの差なら10%程度の上乗せ（＝勝率60%程度）にしてほしい」。

## 問題
シムの「1v1 バランス」セクションで、TOTAL差ごとの強い方の勝率を測定したところ、わずか3〜5点の差で強い方が**74.72%**も勝つ状態だった（差0-2ですら57.81%）。ステータス総合値は本来コレクション画面では非表示にしている数値だが、内部の勝率カーブ自体が急すぎ、「ちょっと強い」程度の差が対戦では大差になっていた。

## 原因の切り分け（シムで実測しながら）
1. **ターン内の乱数（`spread`）を約1.8倍に増やす** → ほぼ効果なし（差0-2: 57.81%→57.41%、差3-5: 74.72%→74.21%）。多ターンの対戦では、1手ごとのブレは大数の法則で平均化され、TOTAL差の「地力」が結局勝敗を支配してしまうため。
2. **ATKだけに試合単位の「調子」係数（±20%）をかける** → 少し効果あり（差3-5: 74.72%→69.89%）だが、DEF/SPD/TEC/LUKなど他のステータスの差がそのまま残るため不十分。
3. **攻守速技運の全ステータスに、試合単位でまとめて「調子」係数をかける** → 大きく効いた。1手ごとの乱数と違い、ゲーム全体（1試合）で1回だけ引く値なのでターン数が増えても薄まらない。

## 実装
- `conditionRoll(beastHash, gameSeed)`：その個体の hash と gameSeed だけから決まる 0.73〜1.27 の乗率。**A/B どちらの引数で渡しても同じ値**になるよう、共有の乱数ストリームではなく個体固有のハッシュから直接計算する（対称性を壊さないため）。
- `applyCondition(fighter, cond)`：`atk/def/spd/tec/luk` の5つ全部に同じ `cond` を掛ける。HP（`maxHp`）は据え置き（「今日の調子」は立ち回りの良し悪しであって、地力・耐久の変化ではない、という位置づけ）。
- `battle()`（1v1）・`squadBattle()`（3v3）の両方に適用。スカッドは前衛・中衛・後衛それぞれが自分の hash から個別に「調子」を引く。

## 結果（シム実測、n=約1万件/帯）
| TOTAL差 | 変更前 | 変更後 |
|---|---|---|
| 0-2 | 57.81% | 55.55% |
| 3-5 | 74.72% | 67.30% |
| 6-9 | 89.03%（WARN） | 80.92% |
| 10-14 | 97.27% | 91.75% |
| 15-20 | 99.67% | 97.74% |
| 21+ | 100.00% | 99.47% |

スカッド（3v3）も同様に緩和（隊差0-2: 60.12%→58.09%、隊差3-5: 80.67%→74.17%）。

## 副作用と調整
全ステータスに乱数を足すと、属性有利・不利の勝率差や熟練度の効果など**他の「差」も同時に薄まる**。属性有利-不利の勝率差が目標レンジ（10〜40pt）の下限を割り込みかけたため、調子係数の振れ幅を微調整（±27%→最終的に0.73〜1.27）して両立させた。ステ型バランス（ATK/TEC/DEF/SPD/LUK）・ガントレット到達段・育成経済など他の指標には目立った影響なし。

## テスト
- `npm run domcheck`：63/63、無修正で通過。
- `npm run sim`：全セクション再検証。**71 PASS / 1 WARN / 0 FAIL**（旧: 70 PASS / 2 WARN / 0 FAIL）——TOTAL差バンドの過大な勝率が解消され、WARNだった項目が1件PASSに転じた分、全体としてはむしろ改善。唯一のWARN（熟練度の勝率上乗せがわずかに負）は許容レンジ内のサンプリングノイズ。

# v11 — 削除が効かない問題（iOSの confirm 無効化）（2026-09-06）

ユーザー報告:「コレクションから削除が機能していない」「iPhoneだとHTMLが上手く使えない」。

## 原因
iOS Safari の一部の文脈（`file://` で直接開いた場合や一部のアプリ内ブラウザ）では `window.confirm()` がダイアログを出さず**常に false を返す**。削除系の処理はすべて `if (!confirm(...)) return;` で始まっていたため、押しても毎回無言でキャンセルされ「機能していない」ように見えていた。

## 修正
- 自前の確認モーダル `cbConfirm(message, onYes)` を新設（`.modal-overlay` を動的生成、「キャンセル」/「実行する」）。端末に依存しない。`window.cbConfirm` として公開。
- `window.confirm()` の呼び出しを全廃：
  - 個体の削除（`data-act="del"`）／欠片化（`data-act="dissolve"`）／挑戦状の削除（`data-rv-del`）／コレクション全削除（`#cb-btn-clear`）→ `cbConfirm` に置換。
  - バックアップの復元（別スクリプトブロック）→ `window.cbConfirm` があれば使い、無ければ従来の `confirm` にフォールバック。復元後の `alert` は `notify`（トースト）＋0.9秒後に `location.reload()` に変更。
- ついでに「コレクション全削除」が `store.rivals` をクリアしていなかったバグも修正。

## テスト
- `npm run domcheck`：確認モーダルの「実行する」/「キャンセル」を押すヘルパ `confirmYes()` を追加。**個体削除の回帰テストを新規追加**（削除ボタン→モーダル表示→確認前は消えない→確認で消える→キャンセルでは残る）。溶解・挑戦状削除・バックアップ復元のテストもモーダル対応に更新。**73 PASS / 0 FAIL**。
- `npm run sim`：無影響。**71 PASS / 1 WARN / 0 FAIL**。

## iPhone で「HTMLが上手く使えない」への回答
`file://`（ファイルアプリ等でHTMLを直接開く）は iOS Safari では機能が制限される環境：`confirm`/`alert` が効かない、カメラ（`getUserMedia`）が使えない、`localStorage` が消えやすい、ダウンロードが不安定、など。**推奨は P1（`docs/計画書.md`）どおり、単一HTMLを無料の静的ホスティングに置いて `https://` の URL を Safari で開くこと**（Netlify Drop にドラッグ＆ドロップ／GitHub Pages 等）。そのうえで「ホーム画面に追加」でアプリのように使える。`dist/BarcodeTool.html` がそのままアップロードするファイル。
